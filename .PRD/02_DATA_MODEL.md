# SoDam-CCC — 데이터 모델 (막힘 카탈로그)

> **이 문서가 제품의 핵심 자산입니다.**
> SoDam-CCC가 다루는 데이터는 "사용자 정보"가 아니라 **"어디까지 됐는가 / 어디서 막혔는가"** 입니다.
> 설치 단계 목록은 세상에 많지만, **막히는 지점을 증상별로 모아둔 것은 없습니다.**

---

## 전체 구조

```
[설치 단계 STEP] --1:N--> [검사 항목 CHECK]
                               ↑
                             1:1
                               |
[증상 SYMPTOM] --1:N--> [원인 CAUSE] --1:N--> [조치 ACTION]
```

읽는 법:
- **STEP** = 설치가 몇 단계까지 왔는지 (진도표)
- **CHECK** = 그 단계가 끝났는지 **기계가 확인할 수 있는 방법**
- **SYMPTOM** = 사용자가 겪는 현상 (사람의 말)
- **CAUSE** = 그 현상의 원인 후보 → 각각 CHECK로 판정 가능
- **ACTION** = 원인이 맞을 때 할 일

> 이 구조가 핵심입니다. **모든 원인은 반드시 검사 가능해야 합니다.** 검사할 수 없는 원인은 카탈로그에 넣지 않습니다 (추측 금지 원칙).

> **🔧 2026-08-19 정정 — 12단계 진도 판정에서 CHK-10 제외**: CHK-10(폰 승인 가능 여부)은 사용자의 진행 상태가 아니라 **플러그인이 그 기능을 지원하는지**를 보여주는 정적 사실입니다. 6단계(플러그인 설치)만 끝나면 페어링·잠금 여부와 무관하게 **항상 통과**하므로, 이 값을 12단계 완료 조건에 그대로 넣으면 아직 안 끝난 사용자에게도 진도가 부풀려 보입니다. 이 PC의 2026-08-17 실측 상태(§FACTS_VOLATILE.md)로 직접 재현 확인: 실제 완료 단계는 8개(1·2·3·4·5·6·8·10)인데, CHK-10을 포함해 세면 9개로 나와 1단계만큼 부풀려졌습니다. 12단계는 이제 **CHK-11 통과 여부만으로 판정**하고, CHK-10은 여전히 검사·표시는 하되 진도 계산에서만 뺍니다.

### 목표치
```
재설치  : 전체 12단계 →  사람 손 3개  (토큰 복사 · 페어링 코드 확인 · 페어링 승인)
신규설치: 전체 12단계 →  사람 손 4개  (+ 4단계 봇 만들기)
```
재설치 시 **4단계(봇 만들기)는 아예 건너뜁니다** — 기존 봇을 그대로 씁니다.

> **🔧 2026-08-09 정정 — 4·5단계 진도 판정 규칙 확정**: 원안은 두 단계의 검사 칸이 `—`(공란)이라 기계가 판정할 수 없었고, 이 상태로는 진도가 **최대 10/12에서 멈춘 것처럼** 보이는 결함이 있었습니다. 봇 생성(4)과 토큰 복사(5)는 **`.env` 파일 존재 여부(CHK-06)로 역추론**합니다 — 토큰이 등록돼 있다면 논리적으로 봇을 만들었고 토큰을 복사한 것이 확실하기 때문입니다. `.env` 내용은 여전히 안 엽니다(C-1 유지).

### ⛑️ 중단해도 안전합니다
각 단계는 **독립적**입니다. 아무 때나 멈춰도 망가지지 않고, 다시 `install` 하면 **이미 끝난 단계는 건너뜁니다.**
> 이 PC의 Discord가 **정확히 그 상태**(8단계에서 멈춤)이고, 그런 상태를 살리는 것이 이 제품의 존재 이유입니다.

> **이 PC의 Discord 실제 상태 = 8단계에서 정지** (토큰 있음 / 페어링 없음). `status`가 이걸 짚어내는 것이 Phase 1 완료 기준 S1입니다.

## 엔티티 3~5: SYMPTOM → CAUSE → ACTION (증상 사전)

> 📖 **이 사전은 `README.md` 의 "문제·오류 대처 방법"(16번)과 "FAQ"(17번)의 원천입니다.**
> README를 쓸 때 **새로 쓰지 말고 여기 내용을 쉬운 말로 옮기기만** 하면 됩니다. → [04_PROJECT_SPEC.md 문서화 요구사항](./04_PROJECT_SPEC.md)

사용자는 "CHK-09가 실패했어요"라고 말하지 않습니다. **"봇이 답을 안 해요"** 라고 말합니다.

### ⚠️ `fix` 의 기본 동작 — 묻지 말고 먼저 찾아라

왕초보는 증상조차 고르지 못합니다. **"그냥 안 돼요"** 라고 말합니다.

```
기본 경로 (권장)  :  검사 15개 전부 실행  →  실패한 것부터 보여줌  →  조치 안내
보조 경로         :  그래도 원인을 못 찾으면  →  아래 증상 사전으로 물어봄
```

> **왜 이 순서인가**: 검사 15개를 전부 돌려도 몇 초입니다. **묻지 않고 먼저 찾아주는 편이** 왕초보에게 훨씬 낫고, 이미 만들어 둔 CHECK 자산을 최대로 활용합니다.
> 증상 사전은 **검사로 안 잡히는 경우**(사양·오해·타이밍)를 위한 보조 수단입니다.

| 필드 | 설명 | 예시 |
|---|---|---|
| id | 고유 번호 | `SYM-01` |
| 증상 | 사용자가 하는 말 | "봇이 아무 반응이 없어요" |
| 원인 후보 | 가능한 원인들 (확률 높은 순) | 4개 |
| 검사 | 각 원인을 판정할 CHECK | CHK-09 → CHK-05 → … |
| 조치 | 원인이 맞을 때 할 일 | "`--channels` 붙여서 다시 실행" |

## 상태 저장 — 무엇을 어디에 쓸 것인가

> **핵심 제약: CCC는 파일을 "직접" 고치지 않습니다.**
> 이 세션에서 안전 가드가 실제로 명령을 2회 차단했습니다. 남의 영역을 직접 건드리면 도구가 못 돕니다.
>
> ⚠️ **단, 공식 명령은 예외입니다.** `/plugin install` · `/telegram:configure` · `/telegram:access …` 는 **원래 `~/.claude/` 에 쓰는 명령**이고, CCC는 이를 **사용자 확인 후 실행**할 수 있습니다. 그 결과 파일이 바뀌는 것은 **정상 동작**입니다.
> → 금지되는 것은 **파일을 직접 열어 고치거나 치환하는 것**입니다. (01_PRD.md §6.3 **G-1 · G-1b · G-1c**)

| 데이터 | 위치 | 읽기/쓰기 |
|---|---|---|
| 채널 설정 (`.env`, `access.json`, `approved/`, `bot.pid`) | `~/.claude/channels/telegram/` | **읽기 전용** (`.env`는 존재 여부만) |
| 플러그인 소스 (`server.ts`, `ACCESS.md`) | `~/…/plugins/cache/claude-plugins-official/telegram/<버전>/` | **읽기 전용** |
| 디버그 로그 | `~/.claude/debug/<세션ID>.txt` | **읽기 전용** |
| 받은 사진 `inbox/` | `~/.claude/channels/telegram/inbox/` | **개수만 셈 — 파일을 열지 않음** (외부 유입 파일이라 신뢰 불가, G-3) |
| ~~CCC 자신의 기록~~ | — | **Phase 1에서는 만들지 않습니다 (A20)** — 아래 참조 |

### 왜 기록 파일을 Phase 1에서 빼는가

| 이유 | 설명 |
|---|---|
| **필요가 없다** | `status`·`fix` 는 **매번 새로 검사**합니다. 과거 기록을 볼 일이 없습니다 |
| **쓸 곳이 마땅치 않다** | 재설치 상황엔 **프로젝트 폴더가 없습니다.** 플러그인은 `~/…/plugins/cache/…` 에 설치되는데 거기는 **읽기 전용 대상**입니다 |
| **위험만 는다** | 기록 파일은 **비밀이 흘러나가기 가장 쉬운 경로**입니다 (문서·저장소로 복사되기 쉬움) |
| **필요해지는 시점이 명확** | "어제 버전과 다른가" 비교가 필요한 **Phase 3(회귀 감시)** 에서 도입하면 충분합니다 |

> ✅ **결과**: Phase 1의 CCC는 **아무 파일도 만들지 않습니다.** 순수하게 읽고 판정하고 안내만 합니다. 가장 안전하고 가장 단순한 형태입니다.

### (Phase 3 도입 시) 기록 파일에 저장해도 되는 것 / 안 되는 것

| ✅ 저장 가능 (판정값) | ❌ 저장 금지 |
|---|---|
| 검사 통과 여부 (`있음`/`없음`/`통과`/`실패`) | **봇 토큰**, `.env` 내용 |
| 버전 번호 (`2.1.226`, `0.0.6`) | **허용목록 사용자 ID** |
| 허용목록 **인원 수** (`1`) | **페어링 코드** |
| 검사 시각 | 파일 **원문**, 디버그 로그 원문 |
| 정책 이름 (`allowlist`) | 전체 경로(홈 디렉터리 이름 포함) |

> 근거: [01_PRD.md §6.3 C-4·D-1](./01_PRD.md#63-보안-요구사항-moscow). 기록 파일은 나중에 문서·저장소로 흘러갈 가능성이 가장 높은 경로입니다.

## 왜 이 구조인가

- **확장성**: Phase 2(상시가동)·Phase 3(회귀 감시)에서 **CHECK 항목만 추가**하면 됩니다. 뼈대(STEP/SYMPTOM/CAUSE/ACTION)는 그대로입니다.
- **단순성**: 데이터베이스가 없습니다. 파일 존재 여부와 텍스트 값만 봅니다. 의존성이 적을수록 research preview 변경에 덜 깨집니다.
- **안 낡음**: 절차를 글로 굳히지 않고 **현재 상태를 검사**하므로, 공식 절차가 바뀌어도 검사 항목만 갱신하면 됩니다.
- **추측 배제**: 모든 CAUSE는 반드시 대응하는 CHECK가 있습니다. 검사할 수 없는 원인은 카탈로그에 넣지 않습니다.
